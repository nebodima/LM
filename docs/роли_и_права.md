# Роли и права «Учёта занятий» (расширение УЗ_ext)

Проверено 28.09.2026 на УНФ 3.0.12, Бухгалтерии предприятия 3.0.174 и Управлении торговлей 11.5.25 (копии
`UZ_UNF_A`, `UZ_BP_C`, `UZ_UT_C`, «Учёт занятий» 2.0.0.1): тест `tools\тесты\тест_права.py` — живые сеансы
менеджера и руководителя с ролями из таблиц ниже, каждый отказ подтверждён журналом регистрации; вход менеджера и
руководителя в веб-клиент во всех трёх конфигурациях, в том числе первый вход после обновления расширения (самый
требовательный к ролям хозяина); в УНФ под менеджером открыты общий журнал, список и форма прихода денег
(«Сформировать текст назначения платежа»), «Взаиморасчёты» — без «Нарушения прав доступа» от «Учёта занятий».
Раньше (копии `UZ_UNF_C`, `UZ_BP_B`, `UZ_UT_B`) под менеджером открывались список и форма урока, карточка педагога,
«Движения документа», РКО, календарь, панель ученика.

## Две роли — как в типовых

| | Менеджер — «Учёт занятий: менеджер» (`УЗ_ОсновнаяРоль`) | Руководитель — «Учёт занятий: руководитель» (`УЗ_Руководитель`) |
|---|---|---|
| Уроки, календарь, помощник и изменение уроков, панель ученика | да | да |
| Ученики и педагоги, группы, предметы, тарифы и цены, абонементы, скидки, дисконтные карты, бонусы, графики педагогов, списание остатков, справочники кассы | да | да |
| Приход денег, перемещение денег | да, документы за свою неделю (граница просмотра кассы) | да |
| Начисления ученикам (набор, материалы, взнос — В15) | да | да |
| Переводы учеников: зачисление в группу, перевод, выбытие (документ «Перевод ученика», В29) | да | да |
| Расход денег (РКО) | только «Касса ученики» (возврат ученику) | все виды |
| Выплата зарплаты, прочий расход, документ «Дополнительные расходы» | нет | да |
| Расходы урока (страница «Доп. расходы» в уроке) | да (урок с расходами не проводится, если по нему уже проведён документ «Доп. расходы»; документ менеджеру не виден — проверку со стороны документа делает проведение руководителя) | да |
| Ставки педагогов, начисления и доплаты педагогам, расчёт зарплаты, отчёт «Расчёты по зарплате» | нет: ставку и начисление в уроке, карточке педагога и группе не видит и не меняет; урок проводит — начисление по ставке пишет проведение (R24) | да |
| Отчёты: взаиморасчёты, явки, аналитика по ученикам, бонусы и карты, ведомость по кассе для менеджеров, движения документа | да | да |
| Плательщики ученика (мама, папа, бабушка), приход денег с расшифровкой платежа (один платёж за нескольких учеников), возврат получателю, отчёт «Оплаты по плательщикам» (этап 2.1, В33–В38) | да (отчёт — по регистру кассы: суммы и за кассу старше границы просмотра, документов в нём нет) | да |
| Полная ведомость по кассе, отчёт по расходам | нет | да |
| Массовая выгрузка и загрузка фото учеников | нет | да |
| Настройки учёта занятий | только чтение | чтение и изменение |
| Даты запрета изменения | только чтение | чтение и изменение |
| Свои напоминания | да | да |
| Рассылка должникам (письма о задолженности, 28.09.2026) | да — как в типовых (УНФ: письма клиентам — работа менеджера); журнал писем — только чтение: запись делает код рассылки, «не чаще N дней» не обойти правкой журнала | да; журнал писем — чтение и изменение |
| Настройки почты (пароль SMTP) | нет | нет — только администратор с «Полными правами» |

Удаление (не пометка) — ни у одной роли: помеченное удаляет администратор.

Что менеджер всё-таки видит и почему:
* **Ставки педагогов читает код урока**, а не человек: при проведении урока начисление педагогу считается по
  ставке. Расширение из файла работает в безопасном режиме, а в нём привилегированный режим не действует — поэтому
  у роли менеджера есть право «Чтение» справочника ставок без права «Просмотр»: справочника нет в его интерфейсе,
  открыть его нельзя, поле ставки и страница «Начисления педагогу» в уроке и карточке педагога скрыты. Это
  **остаток** (R24): суммы ставок программным запросом менеджер прочитать может — ни начислений, ни доплат, ни
  долга педагогу он не видит.
* **РКО выплаты зарплаты** менеджер видит в кассовом журнале и открывает только для просмотра (он отвечает за
  кассу), но создать, изменить или провести его не может.
* Регистр расчётов с педагогами менеджер только пополняет движениями своих уроков, прочитать его не может:
  «Чтение» с условием «ГДЕ ЛОЖЬ». Одного права «Изменение» (как было до 28.09.2026) не хватало — платформа
  считает его и чтением: запрос менеджера читал весь регистр, долги всех педагогов (нашёл живой сеанс
  тест_ревью_зарплата_урока, R24). Регистр расходов — так же (29.09.2026): вкладка «Доп. расходы» урока пишет
  движения, прочитать расходы студии менеджер не может — «Чтение» с условием «ГДЕ ЛОЖЬ» (было одно «Изменение»:
  запрос менеджера читал все расходы, в том числе прочие расходы руководителя; тест_ревью_расходы_урока — отказ по
  журналу, РАЗРЕШЕННЫЕ — 0 строк). Аудит права_роли не пропускает запись без явного «Чтения» ни у одной роли.

### Зарплата в уроке, касса, движения, напоминания (повторный аудит 28.09.2026)

* **Урок начисление педагогу не хранит (R24, 28.09.2026).** Прежде «Начислено педагогу» и таблица «Начисления
  педагогу» лежали в уроке: права на поля прятали их только в интерфейсе, а программный запрос менеджера читал
  их (ограничение чтения поля — «ГДЕ ЛОЖЬ» на поле — закрывает чтение урока целиком: менеджер не открыл бы и не
  провёл урок). Теперь проведение урока считает начисление по ставке (`Документы.УЗ_Урок.НачисленияПоСтавке`) и
  пишет его сразу в регистр «Расчёты по зарплате» — менеджер движения пишет, прочитать регистр не может (отказ по
  журналу регистрации). Доплаты сверх ставки — документ «Начисление педагогам» на основании урока (вкладка
  «Начисления педагогу» → «Добавить доплату», только руководитель); менеджеру он не виден (чтение «ГДЕ ЛОЖЬ») и
  записать его он не может. Вкладку «Начисления педагогу» видит руководитель: начисление по ставке, как его
  запишет проведение, и доплаты урока. «Не изменять» больше нет: сумма «вместо ставки» — ставка урока очищается
  и вводится доплата.
* **Права на поля роли менеджера** (как в ЗУП): суммы ставки («Оплата за занятие», «за час», «с человека», «% с
  оплаты») — без «Просмотр» и «Редактирование»: их нет в форме, в списке и в «Настроить список». «Ставка педагога»
  в уроке, карточке физ. лица и группе — без «Редактирование»; «Просмотр» оставлен: без него платформа не создаёт
  элемент формы, а модули прячут его по имени — форма урока у менеджера не открывалась.
* **Ставку меняет только руководитель — и в обход формы.** Права на поле интерфейсные, поэтому сервер проверяет
  запись: новый урок менеджера получает ставку по умолчанию (группы урока, иначе карточки педагога; другую, в том
  числе скопированную, код заменяет с сообщением); сменить ставку записанного урока можно только вместе со сменой
  педагога или группы и только на ставку по умолчанию, иначе — отказ «Ставку педагога в уроке меняет руководитель»
  (подписка `УЗ_ЗарплатаУрокаПередЗаписью`); ставку в карточке педагога и в группе (новых и записанных) —
  отказ «назначает и меняет руководитель» (`УЗ_ЗарплатаУрока.ПроверитьСтавкуСправочника`). Менеджер заводит
  педагога и группу без ставки — ставку назначает руководитель.
* **Касса менеджера — за его неделю** (ограничение доступа на уровне записей, как в типовых). Приход, расход и
  перемещение денег раньше границы просмотра менеджеру не видны нигде: ни в списках документов, ни в общем и
  кассовом журналах, ни через «Все функции», ни запросом; открыть такой документ нельзя, «Движения документа» по
  нему отвечают «Недостаточно прав для просмотра документа». Граница — «Настройки → Даты запрета изменения»,
  **общая строка** (без пользователя), «Запрет старше N дней»: менеджеру видна касса с «сегодня − N дней»; N = 0 или
  строки нет — видно всё. Граница одна на всех менеджеров и лежит в служебном регистре «Граница просмотра кассы»
  (одна запись); условие роли берёт её подзапросом, поэтому действует в ЛЮБОМ сеансе: веб- и тонкий клиент,
  внешнее соединение (COM, обработки интеграции), фоновые и регламентные задания, HTTP — ничего вызывать заранее
  не нужно. Запись обновляют: регламентное задание «Обновление границы просмотра кассы» раз в сутки (00:05), вход
  сотрудника (если граница посчитана не на сегодня) и шаг первичного заполнения данных (сразу после установки).
  Записи нет совсем — менеджер кассовых документов не видит (строже, а не шире). Своя строка сотрудника в датах
  запрета меняет его запрет изменения и отбор форм (кассовый журнал, «Ведомость по кассе для менеджеров»), но не
  ограничение роли: текущего пользователя в условии роли нет (без параметров сеанса его не узнать). До 28.09.2026
  граница была параметром сеанса, его ставил только модуль приложения — сеанс без клиента падал «Попытка получения
  неинициализированного значения параметра сеанса» (модуль сеанса расширения в безопасном режиме не работает).
* Суммы из старой кассы остаются полными: остатки и долги учеников, оплаты в «Аналитике по ученикам» и форме
  прихода денег считаются по регистрам (движения прихода в регистре «Касса»), а не по документам. Где нужен сам
  документ, он назван словами: во «Взаиморасчётах» — «Документ скрыт (касса раньше вашей даты просмотра)», в
  расшифровке «Аналитики» — «Приход денег от 19.08.2026» без ссылки.
* Условие журнала платформа применяет, только если у роли есть «Чтение» КАЖДОГО документа журнала (проверено
  28.09.2026: иначе условие журнала молча не действует, а ограничения документов журнал не берёт). Поэтому
  зарплатным документам общего журнала (расчёт зарплаты, начисления педагогам, дополнительные расходы) у менеджера
  дано «Чтение» с условием «ГДЕ ЛОЖЬ» — ни одной строки, «Просмотр» не дан, в интерфейсе их нет; условие общего
  журнала само исключает их строки. Офлайн-аудит `права_роли` следит, чтобы у журнала с условием были права на все
  его документы.
* **Движения регистров** вручную не правит ни менеджер, ни руководитель (нет «Редактирование» регистров
  накопления «Учёта занятий»), как в типовых: ручная правка движений — только администратор с «Полными правами».
  Проведение пишет движения само, ему хватает права «Изменение».
* **Напоминания**: свои и общие (о задолженности) — любому; чужие завершить или поставить другому — руководителю.
  Проверку задолженности всей базы запускает регламентное задание или руководитель.
* **Параметры сеанса расширения**: «Песочница почты» (тесты на копиях — письма не уходят, пишутся в журнал) — её
  может включить любой, она только запрещает отправку; «Начало просмотра кассы» — ставит код при входе.
* **Оповещения о задолженности** — по организациям (деньги учеников учитываются раздельно по организациям): аванс
  в одной организации не гасит долг в другой; оповещение «Задолженность Сидорова Анна (Студия Б): 1 000,00» и
  письмо со строкой «Организация: Студия Б.» — на каждую организацию, где ученик должен.

### Как ограничена выплата зарплаты

Ограничением доступа на уровне записей в роли менеджера: права «Добавление», «Изменение» и «Удаление» документа
«Расход денег» даны с условием `ВидОперации = ЗНАЧЕНИЕ(Перечисление.УЗ_ВидыОпераций.КассаУченики)`. Платформа
проверяет его при любой записи — из формы, обработки или внешнего соединения, — отказ пишется в журнал
регистрации («Нарушение прав доступа»). Форма РКО у менеджера предлагает только «Касса ученики», а выплату и
прочий расход открывает только для просмотра. У руководителя условия нет; у пользователя с обеими ролями права
складываются — он работает как руководитель.

### После установки новой версии

Версия выпуска видна в «Администрирование → Расширения конфигурации» (колонка «Версия»): 2.0.0.1, поставщик
«Учёт занятий».
Обновление данных «Учёта занятий» пишет общие настройки, кассы и документы — это права руководителя.
Первым после обновления журнал уроков должен открыть руководитель или администратор; менеджер до этого видит
сообщение «Учёт занятий ждёт подготовки своих данных после обновления: руководителю или администратору открыть
журнал уроков».

### Персональные данные учеников

История изменений справочника «Физ. лица» (ученики, родители, педагоги) выключена: новые версии с датами
рождения, телефонами и заметками не записываются. Версии, записанные до этого обновления, платформа сама не
удаляет. Массовая выгрузка фото — только у руководителя.

## Третья роль — педагог: только своё

«Учёт занятий: педагог» (`УЗ_Педагог`, 28.09.2026) — для педагогов, которые сами отмечают свои уроки. Рабочее место —
обработка «Мои уроки» (раздел «Занятия»): страница «Уроки» (свои уроки за период, явка, тема, домашнее задание) и
страница «Моя зарплата» (свои начисления и выплаты за период, остаток к оплате).

| | Педагог |
|---|---|
| Свои уроки: список, явка, тема, домашнее задание | да — «Мои уроки»; проведённый урок перепроводится (меняются только явки), план записывается и остаётся планом |
| Чужие уроки | нет: не видны ни в «Моих уроках», ни запросом, ни по ссылке; отметки в чужом уроке — отказ «урок другого педагога» |
| «К оплате», цены, абонементы, состав урока, проведение плана | нет — это работа администратора |
| Своя зарплата | да — страница «Моя зарплата»; чужой — нет |
| Отчёт «Расчёты по зарплате» и другие отчёты | нет (см. ниже) |
| Касса, приходы и расходы денег, деньги учеников, списки учеников и педагогов | нет |
| Плательщики учеников и отчёт «Оплаты по плательщикам» (деньги и персональные данные семьи, 2.1) | нет — прав на отчёт нет (аудит права_роли, `ПЕДАГОГУ_ЗАПРЕЩЕНО`; сценарий педагога — отказ) |
| Состав групп: зачисление, перевод, выбытие (документ «Перевод ученика») | нет — прав на документ нет (аудит права_роли, `ПЕДАГОГУ_ЗАПРЕЩЕНО`); регистр состава групп — только «Чтение» коду: запись урока в «Мои уроки» проверяет «в группе на дату» у учеников с «Только выбранные группы» |
| Расчёт зарплаты, выплаты, настройки | нет |

Как устроено:
* **Своё — ограничением доступа на уровне записей.** Урок, график, расчёт зарплаты, начисления педагогам, расход денег
  (выплата) и регистр расчётов с педагогами читаются (урок — и пишется) с условием
  `Т ГДЕ Т.Педагог.Пользователь = &ТекущийПользователь`: педагог урока связан с пользователем программы полем
  «Пользователь программы» карточки педагога (Физ. лица). `ТекущийПользователь` — параметр сеанса хозяина (есть в УНФ,
  БП, УТ), заимствован: его ставит модуль сеанса хозяина в любом сеансе, в том числе без клиента (COM, фон); свой
  параметр сеанса расширение в безопасном режиме не установит. Решение владельца 28.09.2026: это чтение объекта
  хозяина, кода БСП в расширении нет (исключение с обоснованием — в аудите ноль_бсп). Права «Получение» на этот
  параметр у роли педагога НЕТ (снято 28.09.2026): условию ограничения доступа право не нужно, а в безопасном режиме
  расширения право на объект хозяина срезается — платформа писала в журнал «ограничено профилем безопасности» и
  показывала КАЖДОМУ пользователю при входе «Ошибка применения расширения конфигурации» (нашли сценарии
  tools\сценарии; тест права_педагога без права — 46 из 46).
* **Второй рубеж — код «Моих уроков»:** данные и отметки урока другого педагога — отказ с причиной, даже у пользователя
  с широкими правами.
* **Регистр расходов — «Чтение» с условием «ГДЕ ЛОЖЬ»** (29.09.2026): своего в нём у педагога нет, проведение урока
  движения вкладки «Доп. расходы» только пишет. Было одно «Изменение» — платформа считает его и «Чтением»: запросом
  педагог читал все расходы студии (аудит права_роли, `ПЕДАГОГУ_ЧТЕНИЕ_ГДЕ_ЛОЖЬ`).
* **Нет «Просмотр» уроков, физ. лиц, регистров** — списков и карточек в интерфейсе педагога нет; справочники
  (ученики, тарифы, абонементы, ставки) и регистры остатков абонементов и карт — только «Чтение» для кода проведения.
  Регистр состава групп `УЗ_СоставГрупп` (В29, 28.09.2026) — тоже только «Чтение»: запись урока проверяет, что ученик
  с «Только выбранные группы» в группе на дату урока, и эта проверка идёт и в сеансе педагога (отметки явки).
* **Зарплата — страница, а не отчёт.** Отчёт «Расчёты по зарплате» на СКД у педагога пуст: СКД выбрасывает из
  результата поля, у которых нет права «Просмотр» (педагог, документ), а «Просмотр» уроков и физ. лиц открыл бы
  педагогу их списки. Поэтому у роли нет ни отчёта, ни общей формы отчёта, а страница «Моя зарплата» берёт данные
  функцией `Обработки.УЗ_МоиУроки.ЗарплатаПедагога()` (регистр расчётов с педагогами, РАЗРЕШЕННЫЕ).
* **Общий абонемент у двух педагогов.** Проведение урока подбирает абонемент строке «К оплате» и учитывает записанные
  планом уроки по нему — в том числе уроки другого педагога. Этот запрос — РАЗРЕШЕННЫЕ (`Справочники.УЗ_Абонемент.
  ИспользованоАбонементов`): без него перепроведение урока педагогом падало «недостаточно прав» на план другого
  педагога (воспроизведено тестом 28.09.2026). Расход абонемента проведёнными уроками берётся из регистра списаний —
  он читается без ограничения, поэтому остаток абонемента педагог видит полный. Привилегированный режим не
  используется (в безопасном режиме расширения его нет).
* **Роль выдаётся вместе с ролями программы** (как менеджеру — таблица ниже, «Имена ролей в конфигураторе»); другие
  роли «Учёта занятий» педагогу не нужны: права ролей складываются, с ролью менеджера он увидит всё, что видит менеджер.

Проверено тестом `tools\тесты\тест_права_педагога.py` (живой COM-сеанс педагога) и аудитом права_роли (правила
«только своё» — самотест: чтение урока без ограничения, отчёт, «Просмотр» документа — красные). УНФ (`UZ_UNF_B`,
28.09.2026): 46 из 46; живые мутации — ограничение урока снято → 3 красных, РАЗРЕШЕННЫЕ убрано из запроса планов
абонемента → красное «общий абонемент».

**Закрыто 28.09.2026: на копиях БП и УТ (`UZ_BP_C`, `UZ_UT_C`) роль менеджера получал каждый пользователь.**
Причина — в нашем расширении: у УЗ_ext была основная роль (`DefaultRoles` = `УЗ_ОсновнаяРоль`), а в этих базах
у расширения включено «Использовать основные роли для всех пользователей» (`ИспользоватьОсновныеРолиДляВсехПользователей`;
у ПЛ_ext и EF_* — выключено). Тогда платформа даёт права основной роли расширения КАЖДОМУ пользователю в любом клиенте:
`РольДоступна` её не видит, а `ПравоДоступа` и запросы — видят. Загрузка конфигуратором флажок не меняет; БСП хозяина
снимает его только при обновлении ролей пользователей (`УправлениеДоступомСлужебный.ОбновитьРолиПользователей`),
поэтому на УНФ его уже не было, а тесты заводят пользователей мимо БСП. Доказательство (копия UZ_BP_X): пользователь
только с `ЗапускВнешнегоСоединения` — «Чтение» `УЗ_Касса` и «Просмотр» урока есть; флажок снят → нет; флажок снова
включён, но основных ролей у расширения нет → нет. Под администратором `ПравоДоступа(…, ПользовательИБ)` (не зависит
от вида клиента) на UZ_BP_C до исправления — есть, после — нет. Исправление: `<DefaultRoles/>` в
`src_ext/Configuration.xml` (роли выдаются профилями групп доступа; администратору права даёт «Полные права»
хозяина); аудит права_роли краснеет на основной роли расширения (самотест). Тест педагога на UZ_BP_C — 46 из 46,
тест прав менеджера/руководителя — 130 из 130.

## Текст для инструкции покупателю

> **Как дать сотрудникам доступ к «Учёту занятий».**
> В «Учёте занятий» две роли: **«Учёт занятий: менеджер»** — администратор студии на ресепшене (уроки, ученики,
> абонементы, приём денег, возврат денег ученику, календарь, отчёты по урокам и явкам) и **«Учёт занятий:
> руководитель»** — всё, включая зарплату педагогов, расходы, настройки, даты запрета и все отчёты. Третья роль,
> **«Учёт занятий: педагог»**, — для педагогов: только свои уроки (явка, тема, домашнее задание) и своя зарплата в
> обработке «Мои уроки»; в карточке педагога руководитель указывает «Пользователь программы» — под ним педагог входит.
> Роли выдаются через профили групп доступа (профиль педагога — те же роли программы и роль «Учёт занятий: педагог»).

>    **Скопировать**, назовите копию, например «Продажи и учёт занятий», и дальше работайте с копией.
> 3. На закладке с ролями (**Разрешенные действия**) отметьте **«Учёт занятий: менеджер»** (руководителю —
>    **«Учёт занятий: руководитель»**). Нажмите **Записать и закрыть**.
> 4. Если делали копию — в **Группы доступа** переключите группу сотрудника на новый профиль.

в самом требовательном случае — первый вход в программу после обновления расширения (хозяин тогда обновляет параметры
работы программы под входящим сотрудником и читает больше, чем при повторном входе; при повторном входе УНФ пускала и
без `ЧтениеКурсовВалют`, `БазовыеПраваБТС`, `БазовыеПраваПриложения`). Первым входом после обновления:

  организацию в документах и печатает её реквизиты;
* УТ — набор из таблицы, входят менеджер и руководитель.
`ВыводНаПринтерФайлБуферОбмена` и `СохранениеДанныхПользователя` для входа не нужны — это печать и сохранение
настроек сотрудника, они есть в каждом поставляемом профиле. COM-соединение отказов старта не замечает, поэтому наборы
проверены входом в веб-клиент (пробный пользователь с набором ролей, вход по адресу своей публикации с параметром `?N=` и именем пользователя; каждый
«первый вход» — после загрузки расширения с изменённым модулем).

менеджерской: зарплата, расходы, настройки и даты запрета из неё ушли в «Учёт занятий: руководитель».

`ЗапускВнешнегоСоединения` тест выдаёт только себе (COM-подключение); покупателю она не нужна.

**Клиент-серверная база — наборы те же (В44, 30.09.2026).** Роли хозяина сверх таблицы не нужны: на копии БП в кластере
(`uz_bp_srv`) менеджер с набором из таблицы в рабочем процессе сервера (так пишут формы тонкого и веб-клиента; в тесте —
фоновое задание его сеанса) заводит ученика, предмет, тариф и перепроводит урок. Константу хозяина
`ПроверятьИспользованиеУдаляемыхОбъектов` подписки БСП читают в привилегированном режиме — права на неё нет ни в одной
роли хозяина, кроме «Полные права», и не нужно. Отказы бывают только во **внешнем соединении (COM) под сотрудником** к
клиент-серверной базе: там код хозяина и `ПередЗаписью` исполняются в процессе COM, привилегированный режим не действует —
любая запись сотрудника падает «Нарушение прав доступа» (и в справочник хозяина, без нашего расширения). Интеграции через
COM запускать под администратором; как с этим живёт `тест_права` — docs/проверки.md, «Серверная копия БП».

Администратор с ролью «Полные права» работает со всем, включая настройки почты; наши роли ему не нужны.

## Что проверяет код, а не роль

* `УЗ_Общий.ДоступнаЗарплата()` — право изменения расчёта зарплаты (руководитель, «Полные права»). По нему
  форма урока прячет ставку и страницу «Начисления педагогу», карточка педагога и группа — ставку, форма РКО —
  выплату и прочий расход; без него сервер не даёт сменить ставку урока, карточки педагога и группы
  (`УЗ_ЗарплатаУрока`).
* `УЗ_ОбработкаФото` — выгрузка и загрузка фото начинаются с `ВыполнитьПроверкуПравДоступа("Использование", …)`:
  экспортную функцию модуля менеджера платформа даёт вызвать и без права на обработку (проверено тестом).
* Отчёт «Движения документа» показывает только регистры, которые пользователь может читать, и только для
  документа, который пользователю виден (запрос с РАЗРЕШЕННЫЕ: касса старше границы просмотра — отказ). Регистр с
  «Чтением» «ГДЕ ЛОЖЬ» (расчёты с педагогами, расходы у менеджера) `ПравоДоступа` считает недоступным — его в отчёте
  нет; регистр с другим условием чтения отсекает РАЗРЕШЕННЫЕ в обоих запросах отчёта (добавлены 29.09.2026; до того
  такой регистр уронил бы отчёт «Недостаточно прав»). Проверка — тест_ревью_расходы_урока: до 29.09.2026 менеджер
  видел в «Движениях документа» урока расходы руководителя.
* Обновление данных (`УЗ_ОбновлениеДанных`) идёт только у того, кто может записать настройки и версию данных.

## Безопасность

* **Пароль SMTP хранится в базе строкой** — в регистре сведений «Настройки почты» (`УЗ_НастройкиПочты`), без
  шифрования: у расширения без БСП нет безопасного хранилища, решение владельца 28.09.2026 — оставить так. Прав на
  регистр и форму настроек почты нет ни у менеджера, ни у руководителя (офлайн-аудит `права_роли`, тест прав: запись —
  отказ по журналу регистрации); форма настроек сохранённый пароль не показывает, записывает его только администратор.
  Но администратор с «Полными правами» может прочитать пароль (консоль запросов, «Все функции»), и его может прочитать
  любой, у кого есть копия базы: файл `1Cv8.1CD`, выгрузка `.dt`, резервная копия SQL. Поэтому: для рассылки заведите
  отдельный почтовый ящик и пароль приложения почтового сервиса (не пароль основной почты); передавая копию базы
  сторонним (разработчику, на проверку), сначала очистите пароль в «Настройки почты»; при увольнении администратора
  смените пароль ящика.
* **Ключи провайдеров сообщений** (токен бота Telegram, ключ SMS.ru, логин и пароль SMSC.ru, ключи Green-API и
  Wazzup; этап 2.2, В48) хранятся так же, как пароль SMTP — строкой в регистре `УЗ_КлючиКаналов` без прав у ролей:
  руководитель вводит ключ в «Каналах сообщений» (поле пароля, сохранённый ключ не показывается), читает его только
  код отправки; в журнал регистрации и журнал сообщений ключ не пишется. Для копии базы у стороннего — сначала
  очистить ключи (или отозвать токен у @BotFather, сменить ключ в кабинете провайдера).
* **Сообщения семьям** (этап 2.2): руководитель — «Каналы сообщений» (каналы, шаблоны, проверка, «Отправить
  напоминания сейчас»); менеджер — «Сообщение ученику», «Журнал сообщений» (только чтение), ссылка Telegram в
  карточке (регистр привязок — чтение и запись); педагог — ни привязок, ни журнала, ни отправки.
* **Касса старше границы просмотра** закрыта ограничением доступа на уровне записей (см. выше); суммы, которые из неё
  складываются (остатки, долги, аналитика), менеджер видит — это итоги, а не документы.
* **Ручная правка движений** регистров «Учёта занятий» — только «Полные права»; сотрудники меняют учёт документами,
  которые проверяют даты запрета.
* **Расширение работает в безопасном режиме** (так 1С ставит расширение из файла): привилегированного режима у кода
  нет, всё читается и пишется с правами самого сотрудника; внешние ресурсы — только почта через песочницу.
  В безопасном режиме Telegram, SMS и WhatsApp не работают вовсе (платформа запрещает HTTP): форма «Каналы
  сообщений» и регламентное задание говорят, как его снять.
