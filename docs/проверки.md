# Опись проверок «Учёта занятий» (УЗ_ext)

Опись сверяет сам аудит `скрипты` (`tools/аудиты/скрипты.py`): каждый аудит и каждый COM-тест
на диске обязан быть назван здесь, каждый путь `tools/…/*.py` в `docs/*.md` — существовать.
Добавил проверку — допиши строку сюда, иначе все_аудиты покраснеет.

## Как запускать

    python tools/аудиты/все_аудиты.py              # все офлайн-аудиты src_ext, бюджет ≤ 5 с (печатается)
    python tools/аудиты/самотест.py                # каждая проверка обязана краснеть: мутации на фикстурах
    python tools/прогон.py                         # COM-тесты tools/тесты/тест_*.py на УНФ, БП, УТ (с двойниками UZ_*_2)
    python tools/прогон.py --без-двойников         # каждая база одним процессом (дольше; для сравнения)
    pwsh -File tools\агенты.ps1                    # процессы 1cv8: свои агенты (простой, сторож) и чужие
    pwsh -File tools\агенты.ps1 -Остановить -Все   # остановить свои агенты (или -База УНФ | UZ_UNF_K | C:\1c_bases\…)
    python tools/прогон.py --база=C:\1c_bases\UZ_UNF_B --пользователь=Администратор --тест=аудит_данных
    pwsh -File tools\деплой.ps1 -СвояБаза C:\1c_bases\UZ_UNF_D          # загрузка расширения в свою копию
    pwsh -File tools\деплой.ps1 -СвояБаза C:\1c_bases\UZ_UNF_D -НесмотряНаАудит   # осознанно при красном аудите (с 28.09 аудиты 0)
    python tools/убрать_сирот.py --база=C:\1c_bases\UZ_UNF_D            # сироты в регистрах УЗ_: отчёт
    python tools/убрать_сирот.py --база=C:\1c_bases\UZ_UNF_D --исправить  # …и уборка
    python tools/мутации_проверок.py --база=C:\1c_bases\UZ_UNF_D        # COM-проверки краснеют (8 мутаций, ~3 мин)
    pwsh -File tools\мутации_гейта.ps1 -База C:\1c_bases\UZ_UNF_D       # гейты деплоя краснеют (~2 мин)

Самотест: чистые фикстуры (`tools/аудиты/фикстуры`) — 0 замечаний во всех аудитах; в копию подкладывается
ровно одна ошибка — нужный аудит даёт ровно одно замечание; «почти ошибки» — ни одного. Аудит без мутации
самотест считает провалом. Фикстуры с 28.09 — документ, справочник, регистр, общий модуль, **отчёт со схемой
СКД и обработка с формой** (5 мутаций — на отчёт и обработку: обработчики, элементы_форм, bom,
повторы_тегов, права_роли) и **справка F1** — страницы формы документа, справочника, обработки, объектов и
раздела (15 мутаций на аудиты справка, полнота_справки, подписи_справки). С повторного аудита 28.09: вопрос
«Да/Нет», канал наружу (HTTPСоединение, ИнтернетПочта вне УЗ_Почта, Послать без песочницы — на модуле почты,
который мутация кладёт в копию фикстур), Edit регистра у менеджера, справка о проводках — **всего 100 мутаций,
19 контролей**. Правила права_роли, которые на фикстурах не срабатывают (поля зарплаты, кассовый журнал,
параметры сеанса), и правила внешний_мир на настоящем УЗ_Почта проверены ручными мутациями копии src_ext —
8 из 8 красные (28.09.2026).

## Деплой (tools/деплой.ps1): гейты и время

Порядок: офлайн-проверки параллельно (проверка src_ext, все аудиты, самотест аудитов — самотест только если
`tools/аудиты` изменились с последнего зелёного: кэш по отпечатку содержимого) → **красное — СТОП до загрузки**
(исключение — ключ `-НесмотряНаАудит`, печатается ПРЕДУПРЕЖДЕНИЕ) → на каждую базу: замок → загрузка →
`/CheckModules` (до применения) → применение → отметка деплоя.

| Что | Как устроено |
|---|---|
| разбор результата | не по словам. Пакетная загрузка/применение — зелёные, только если код 0 **и журнал /Out пуст** (при успехе платформа молчит, любой текст печатается целиком). `/CheckModules` — код 0, «Синтаксических ошибок не обнаружено» и ни одной строки `{Модуль(стр,кол)}:`. Агент — строка ответа вида `Ошибка ConfigFilesError - …` |
| таймауты | каждый шаг — 3× своего бюджета, процесс снимается, шаг красный |
| замок | `%TEMP%\уз_прогон\c_1c_bases_uz_unf_d.lock` (для UZ_UNF_D), байт 0 — тот же, что у прогона: деплой и прогон в одну базу не идут одновременно, второй ждёт до 3 мин и печатает ожидание |
| частичная загрузка | отпечаток «длина\|время» файлов прошлой удачной загрузки в эту базу; новые/удалённые файлы, Configuration.xml, другая папка, чужая заливка — полная. Отпечаток снимается перед загрузкой и пишется только после применения: после упавшей загрузки или красного гейта следующий деплой — полный |
| агент конфигуратора | `tools/агент_конфигуратора.py`: папка `%TEMP%\uz_agent\UZ_UNF_D` (ASCII, по имени папки базы), порт — свободный из 1546–1560, владелец порта сверяется по pid (1543 — агент DO_3, 1545 — ras). Выбор порта — под общим замком `%TEMP%\uz_agent\порты.lock` с учётом портов агентов других баз, которые ещё поднимаются (параллельный деплой). После `update-db-cfg` перезапуск в фоне — со сторожем простоя (ниже «Агенты конфигуратора»); `-ПростойАгента 0` — не перезапускать, остановить по окончании деплоя. Любой отказ — пакетный конфигуратор |
| зеркало для агента | агент грузит только из-под своего `/AgentBaseDir`: из `C:\Users\User02\LESSONS_MANAGER\src_ext`, `%TEMP%`, `C:\1c_run` и самой папки агента он отвечает «Ошибка разбора параметра: dir / Directory access violation» и печатает справку по всем командам (проверено 28.09.2026 на UZ_UNF_E; каталог процесса агента не влияет). Поэтому деплой держит зеркало `%TEMP%\uz_agent\UZ_UNF\src`: копирует только изменённые файлы (время сохраняется), лишние удаляет; список частичной загрузки — пути в зеркале. Из-за этого на основных базах каждый деплой уходил в пакетный режим (163 с на три базы) |
| три базы | `-Базы УНФ,БП,УТ` — офлайн-проверки один раз, затем дочерний деплой на базу параллельно (свой замок, агент, порт); таймаут дочернего — 3× бюджета цикла. `-Копии _E` — то же на `C:\1c_bases\UZ_UNF_E`, `UZ_BP_E`, `UZ_UT_E` |
| «в базе то, что в src_ext» | `tools/отпечаток_src.py`: деплой пишет отметку (sha256 src_ext) в `%TEMP%\уз_прогон\c_1c_bases_uz_unf_d.деплой.json`; прогон первым пунктом «расширение» сверяет отпечаток рабочей копии с отметкой и ХешСумму УЗ_ext в базе с привязанной первым прогоном. Нет отметки / src изменён после деплоя / расширение перезалито мимо деплоя — красное. `--без-сверки` — осознанно |

Мутации гейта (`tools/мутации_гейта.ps1`, 28.09.2026, база UZ_UNF_D): «Проба = ;» в общем модуле — «проверка
модулей ОШИБКА», в базу не применено; тип реквизита на несуществующий справочник в XML — «загрузка ОШИБКА»
(агент, затем пакетно); «Для И = 1 По 2» без ключа — «СТОП до загрузки». **Не ловится загрузкой** (платформа
молча принимает): неизвестный элемент `<НеверноеСвойство>` в XML и неверное булево `<Hierarchical>неверно`.

Время цикла на UZ_UNF_D (28.09.2026): было 49 с (полная загрузка 12,7 + применение 11 + проверка модулей 19,3 —
три пакетных запуска, модули проверялись после применения). Стало: изменений нет — 2,4 с; частичная (1 файл) —
36 с; полная через агента — 36–41 с; откат на пакетный конфигуратор — 53–63 с. Главное время теперь —
`/CheckModules` 19–20 с (≈12 с старт и загрузка метаданных УНФ + ≈3–4 с на режим), у агента такой команды нет.

Три базы (копии основных UZ_UNF_E/UZ_BP_E/UZ_UT_E, 28.09.2026): было 163 с (по очереди, агент отказывал — всё
пакетно, применение 11–12 с). Стало параллельно: 58,3 с при холодных агентах (старт агента 7,8 с), 44,1 с при
тёплых и полной загрузке; применение через агента 5,5–7,4 с (бюджет 10). Мутации гейта на UZ_UNF_E — 3 из 3.

## Агенты конфигуратора: сторож простоя и ручное управление

Было (28.09.2026): деплой перезапускал агента после каждого применения «к следующему деплою» и не останавливал
никогда — по агенту на каждую копию (A–E, _K…) и основные базы. Насчитали 15 процессов 1cv8: кончились лицензии,
прогоны падали 0xC0000409 «Ключ защиты программы больше не доступен», мешали соседнему проекту.

Стало (`tools/агент_конфигуратора.py`):
* вместе с агентом стартует **сторож** — отвязанный процесс python (`агент_конфигуратора.py сторож`): раз в 15 с
  смотрит отметку `%TEMP%\uz_agent\<база>\активность` (её трогают старт и каждая команда агенту) и останавливает
  агента, простоявшего без команд дольше предела; выходит сам, если агента уже нет или агент базы заменён новым.
  Журнал — `%TEMP%\uz_agent\<база>\сторож.log`;
* предел — `-ПростойАгента` деплоя в минутах, по умолчанию 10 (или переменная `UZ_АГЕНТ_ПРОСТОЙ_МИН`); за это
  время следующий деплой берёт тёплого агента (без ~6 с старта). `-ПростойАгента 0` — агент не переживает деплой:
  не перезапускается после применения и останавливается в `finally` при любом исходе;
* страховка на убитого сторожа: каждый старт агента останавливает простоявших дольше предела агентов других баз;
* трогаются **только свои**: процесс 1cv8 в `/AgentMode`, база `C:\1c_bases\UZ_*`, папка агента в `%TEMP%\uz_agent` —
  по командной строке процесса. Агент DO_3 (docmngr3, порт 1543), пакетные конфигураторы других сессий и всё
  прочее в списке помечены «чужой — не трогаю». Агенты старого образца (без отметки активности, запущены до этой
  правки) сторож и уборка не трогают — их простой неизвестен; снимать `агенты.ps1 -Остановить`.

Ручное управление — `tools/агенты.ps1`: без ключей / `-Список` — все процессы 1cv8 (свой агент: база, порт, минут
без команд из предела, жив ли сторож); `-Остановить -Все` — все свои; `-Остановить -База УНФ` (или `UZ_UNF_K`,
или полный путь) — одной базы. Без `-Все`/`-База` — отказ.

Проверено 28.09.2026 на копиях UZ_*_K: деплой трёх баз `-ПростойАгента 1` — после деплоя 3 агента со сторожами,
через 60 с все три остановлены сторожами («без команд 60 с (предел 60 с) — остановлен»), агенты основных баз,
UZ_TEST и DO_3 не тронуты; `-ПростойАгента 0` — сразу после деплоя агентов _K нет (ошибка найдена этой проверкой:
сторож с пределом 0 снимал агента посреди деплоя — теперь при 0 сторож не ставится, уборка такие не трогает);
по умолчанию (10 мин) — деплой в 05:51:37, сторожа остановили все три агента в 06:01:38 («без команд 600 с»), процессов 1cv8 по UZ_*_K не осталось. `агенты.ps1 -Остановить -База C:\1c_bases\docmngr3` — «остановлено 0».

## Прогон (tools/прогон.py)

Замок общий с деплоем; ожидание занятой базы печатается и в итоге («ожидание занятой базы N с») — таймаут
на него продлевается, бюджет молча не съедается. Жёсткий таймаут процесса базы — 3× бюджета (135 с) + ожидание:
процесс снимается, база «ТАЙМАУТ». Тест без единой проверки — провал. `аудит_данных` идёт последним: после
уборки всех тестов на чистой базе он обязан быть зелёным. После КАЖДОГО теста `сеанс.py` сверяет число
регистраторов-сирот в регистрах УЗ_ до и после (≈0,05 с, вне бюджета) — прибавилось → красное. Журнал своей
копии — `СВОЯ_UZ_UNF_D.log` (прогоны разных копий не затирают друг друга).

Проверено 28.09.2026 на UZ_UNF_D: `--таймаут=12` — «ТАЙМАУТ: процесс базы снят через 13 с», код 1; деплой
во время прогона ждал замок 15 с с печатью; прогон во время деплоя ждал 30 с («ожидание занятой базы 30 с (вне
бюджета)»). Мутации `tools/мутации_проверок.py` — 8 из 8 краснеют (сироты, точная сумма долга, причина отказа
урока, причина отказа печати, цифры четырёх отчётов, цифры отчёта сотрудника, сверка src, сверка ХешСуммы).
Полный прогон: UZ_UNF_D — 11 из 11 зелёных, 36,6 с; копия УТ UZ_UT_D — 11 из 11, 33,1 с.

Три базы, 25 тестов (копии, `--копии=_E`, 28.09.2026): 53,1 с при цели 45. Путь одной базы ≈ 51 с = подключение
7,5 + сценарии 37–40 с; из них тест_права ≈ 16 с (запись пользователя в холодном сеансе 4,4 с, подключение
сотрудника 2,3–3,0 с, первый отчёт СКД в новом сеансе 4,8 с — ФабрикаXDTO), первый СКД в тест_отчеты ≈ 4 с,
контроль сирот всего ≈ 1 с. Пробовал делить тесты базы на два COM-сеанса (общие настройки и аудит_данных —
отдельно, после): 45,2 с, но во втором прогоне «Конфликт блокировок при выполнении транзакции: Не удалось
заблокировать таблицу» — файловая база держит блокировку на таблицу, параллельные записи двух сеансов
конфликтуют. Отказался: проверка, которая краснеет от соседа, хуже медленной. Остаток до 45 с без ослабления —
только в продукте/стенде: серверные базы вместо файловых или постоянный тестовый пользователь (минус 4,4 с).

### Скорость: двойники баз, P-ядра, предел лицензий (28.09.2026)

Разложение по тестам (журнал прогона, поле «полное» в `%TEMP%\уз_прогон\УНФ.json` — с подключениями сотрудников
и контролем сирот): УНФ одним процессом ≈ 63–69 с = подключение 7–8 + работа ≈ 56–62, из неё тест_права ≈ 19–25 с
(сценарий 6–7,5 + вне бюджета 12–18: заведение пользователей в холодном сеансе 4–5,4, вход сотрудника 2,2–2,4 × 2,
первый отчёт СКД в сеансе каждого сотрудника ~4), тест_отчеты 5–7 (первый СКД сеанса), остальные 27 тестов ≤ 3,5 с.
Вывод: упор — последовательная очередь тестов в одном сеансе, а не отдельный тест.

Что сделано (проверки те же, ни одна не выключена):
* **двойник базы** — копия файла `1Cv8.1CD` рядом (`UZ_UNF` → `UZ_UNF_2`; для `--копии=_K` — `UZ_UNF_K_2`). Тесты
  базы делятся на две группы по времени прошлых прогонов (`время_тестов.json`, сглаживание 1:1) и идут
  одновременно в основной базе и в двойнике — разные файлы, блокировок таблиц нет (в отличие от прошлой пробы двух
  сеансов в ОДНОЙ базе, см. выше). В обеих группах — сверка расширения своей базы, контроль сирот после каждого
  теста и `аудит_данных` в конце; проверка запросов — в основной. Двойник копируется только после деплоя основы
  (запись `…_2.двойник.json` хранит отметку деплоя, с которой снят), копии трёх баз — параллельно, 1–3,3 с
  (УТ 6,7 ГБ); получает ту же отметку деплоя, ХешСумму привязывает сам. Копирование — под замками основы и
  двойника; двойник открыт зависшим процессом — прогон этой базы одним процессом, с печатью;
* **P-ядра без EcoQoS**: процесс базы (COM-сеанс 1С живёт в нём, один поток) — на первые логические процессоры
  восьми P-ядер i9-14900KF (EfficiencyClass из GetSystemCpuSetInformation), EcoQoS выключен. Без этого 6 процессов
  разъезжались по E-ядрам: 57,3 с против 48,9 с при загрузке процессора ~20 % и диска < 100 МБ/с (замер psutil);
  `--все-ядра` — отключить;
* **предел клиентов 1С = 14** (`UZ_ПРЕДЕЛ_КЛИЕНТОВ_1С`): проба — 6 и 9 одновременных COM-сеансов в разных
  процессах (по 15 с, запрос в секунду) при 5 процессах 1cv8 — ни одного отказа (всего 14 клиентов); инцидент
  с ключом был при ~15 процессах 1cv8 + 3 COM. Выше 14 не проверял сознательно: проба «до отказа» роняет чужие
  сеансы (DO_3, сеанс владельца в UZ_TEST). Прогон считает процессы 1cv8 и процессы баз других прогонов; двойники
  даются стольким базам, сколько влезает, остальным — ПРЕДУПРЕЖДЕНИЕ и один процесс. Третья копия на базу (9
  процессов) не сделана: 9 COM + агенты выходят за проверенный предел и за 8 P-ядер, а упор всё равно тест_права
  ≈ 25–30 с + подключение ≈ 8.

привязанной ХешСуммы двойника — «УНФ_2 расширение … ≠ привязанной», код 1. Цель ≤ 45 с не достигнута: путь
группы с тест_права = подключение ~8 (под нагрузкой до 10) + права ~25–30 + аудит ~3; дальше — только сокращение
холодных трат самого теста прав (вход сотрудников и первый СКД в их сеансах) или серверные базы.

Сироты в базах A/B/C/UZ_UT были от `тест_права`: он удалял ПКО и уроки сотрудника с `ОбменДанными.Загрузка =
Истина`, а в этом режиме платформа движения документа НЕ удаляет (опыт на UZ_UNF_D: «движений до 1, после
удаления 1», без Загрузки — 0). Теперь `сеанс.удалить_объект` снимает движения по всем регистрам документа сам.
Мутация (вернуть удаление без снятия движений) — тест_права красный «после теста нет новых сирот».

   `УЗ_ПеремещениеДенег` с условием `ГДЕ Дата >= &УЗ_НачалоПросмотраКассы` в роли менеджера (журналы тогда
   фильтруются сами). Перед этим (зона агента кассы/отчётов): запросы без РАЗРЕШЕННЫЕ по этим таблицам
   падут «Нарушение прав доступа» — форма ПКО (сумма оплат ученика, Documents/УЗ_ПриходДенег/Forms/ФормаДокумента,
   запрос `СУММА(ПКО.СуммаДокумента)`), отчёт «Аналитика по ученикам» (форма, два запроса к ПКО), отчёты с
   `Регистратор.…`; параметр сеанса нужно ставить при начале работы (модуль приложения расширения → серверный
   вызов `УЗ_ДатыЗапрета.ГраницаПросмотра`), а не только в форме кассового журнала. Приёмка: тест_права — старый
   ПКО не виден в общем журнале и списке ПКО, карточка ученика и отчёты менеджера открываются без ошибок; веб-клиент.
2. **T06 в деплое:** шаг «отметка деплоя» в tools\деплой.ps1 звать с `--хеш-из-базы --пользователь=Администратор`
   (копии БП — `--пользователь=1`, УТ — `--пользователь=Admin`: то же, что ключ деплоя -Пользователь) (+≈6 с на COM-подключение). Зона агента инструментов.
3. **S02 для руководителя и прямой записи наборов:** руководителю «Редактирование» регистров оставлено (он же
   меняет даты запрета). Если владелец решит закрывать и это — подписка ПередЗаписью наборов записей регистров
   УЗ_ с проверкой даты регистратора (`УЗ_ДатыЗапрета.ПричинаЗапрета`). На серверной базе проверить ручное
   редактирование движений под обеими ролями.
4. **S05 (пароль SMTP строкой):** в копии базы пароль читаем администратором. Без БСП у расширения нет безопасного

   сервере (переменная окружения/файл вне базы). Решение владельца.
