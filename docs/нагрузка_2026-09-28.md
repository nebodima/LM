# Нагрузочная проверка УЗ_ext на объёмах студии за 3 года (28.09.2026)

Ответ на N07/A11/Q04–Q05 повторного аудита Codex («замеры на 30 000 уроков»). Замеры сделаны на файловой копии УНФ с
расширением, через COM (внешнее соединение, один сеанс). Мерилась серверная часть: запросы, проведение, формирование
отчётов. Отрисовку в клиенте, веб-клиент, клиент-серверную базу и параллельные сеансы здесь не мерили (см. «Чего нет»).

## Стенд и как повторить

База `C:\1c_bases\UZ_PERF` — копия `UZ_UNF` (Администратор без пароля) с актуальным расширением (src `9210460e5bd7`).
Базу оставил: на ней можно повторять замеры после правок.

```
pwsh -File tools\деплой.ps1 -СвояБаза C:\1c_bases\UZ_PERF -БезСборки -Полная
python tools\нагрузка\наполнить.py                      :: наполнение с нуля (~25 мин), возобновляется после обрыва
python tools\нагрузка\замеры.py                         :: все замеры (~15 мин, из них 6,5 мин — «Явки» за 3 года)
python tools\нагрузка\замеры.py --только=урок,отчеты    :: выбранные разделы
python tools\нагрузка\замеры.py --только=диагностика    :: разбор СКД-отчётов по этапам (запрос / вывод)
python tools\нагрузка\замеры.py --только=опыты --опыты=аб   :: A/B «Взаиморасчётов» (детальные записи, текст запроса)
```

После правок `src_ext` достаточно деплоя без `-Полная` (загрузит изменённое). `-Полная` нужен после копирования
файла базы: отметка деплоя хранится в `%TEMP%`, а не в базе, и без ключа деплой ответит «изменений нет», не загрузив
расширение в новый файл.

Результаты пишутся в `C:\1c_bases\UZ_PERF\`: `нагрузка_наполнение.json` (по месяцам) и `нагрузка_замеры.json`
(замеры, тексты запросов СКД, опыты).

Все тексты запросов замера сначала проверяются по метаданным базы (`НайтиПараметры`): 25 текстов, 0 ошибок. Самотест
проверки — 3 заведомо неверных запроса, пойманы все 3 из 3.

## Наполнение: скорость

Проводилось настоящим проведением, в хронологическом порядке. Поэтому все контроли (касса не в минус В14, остаток
абонемента, пересечения педагога и помещения) работали как у живой студии.

- Скорость — **31 документ/с** в среднем: от 24 до 40 по месяцам. Это 37 месячных замеров, около 35 000 документов.
- Проведение урока внутри потока:
  - **29,6 мс** в начале (окт.–дек. 2023);
  - **35,6 мс** на полной базе (июль–сент. 2026).
  - За 3 года данных — +20 %, рост пологий.
- Отказов проведения — 5 из ~46 000. Все пять — «перенос денег ученика между предметами больше остатка». Это верный
  контроль C02/В12, а не дефект.
- Лицензия на машине общая. За время наполнения ключ защиты пропадал **17 раз** («Ключ защиты программы больше
  не доступен»). После потери ключа COM в том же процессе не оживает. Поэтому процесс-сторож перезапускает дочерний
  процесс, и тот продолжает с непроведённых событий. У каждого документа в комментарии стоит `_Нагрузка #<ид>`.

Q04 (цена по строкам) на 30 000 уроков узким местом не стал: 16 вызовов по 1 мс.

**Как мерились формы.** Модуль формы через COM не вызвать. Поэтому серверную часть календаря, панели и помощника
повторяет внешняя обработка `tools\нагрузка\ЗамерыФорм.bsl`. В ней те же запросы и те же обращения через точку в
циклах, что в `src_ext`; номера строк указаны в комментариях. Отчёты со своей формой идут через существующий
`tools\тесты\стенд_форм.py` — это сам модуль формы. Первое чтение макета СКД в сеансе (~4,4 с, фабрика XDTO) в замеры
не входит.

**Шум.** Машина общая: параллельно шли тесты других агентов, загрузка ЦП 25 %. Одиночные выбросы — до ×3. Пример:
«Взаиморасчёты» за год в шести подряд прогонах — 5,2…16,7 с. Для решений использованы попеременные A/B-серии в одном
сеансе, а не одиночные числа.

### 1. УЗ_Явки_2 — условное оформление проверяет «Период заполнено» в каждой ячейке сетки дней

**Файл:** `src_ext/Reports/УЗ_Явки_2/Templates/ОсновнаяСхемаКомпоновкиДанных/Ext/Template.xml`, строки 279–388.
Это условное оформление варианта, два элемента: «Явка > 0 И Период заполнено» → зелёный; «Явка = 0 И Период
заполнено» → «-» на оранжевом. Условие «Период» — строки 294–297 и 346–349.

**Почему дорого.** Таблица: строки — ученики, колонки — дни с дополнением периода по дням (строки 454–471). Условие по
полю группировки колонок вычисляется для каждой ячейки. За год это 1 147 × 398 ячеек, за 3 года — 1 855 × 1 129.

**Разбор по этапам (год):**
- запрос набора — 0,6 с (35 тыс. строк);
- формирование целиком (запрос + компоновка + вывод) — 29,7 с.

| **Оформление в группировке колонок «Период»** | **3,4 с** | **16,8 с** |
| Без оформления вовсе | 3,2 с | — |
| Без дополнения днями, оформление как есть | 9,1 с | — |
| Квартал / месяц как есть | 2,1 с / 0,6 с | — |

**Патч** (смысл оформления сохраняется; колонка итога по строке остаётся без цвета, как сейчас):
1. Вырезать блок `<dcsset:conditionalAppearance>…</dcsset:conditionalAppearance>` (строки 279–388) из уровня варианта.
2. Вставить его внутрь `<dcsset:column>` таблицы — после `</dcsset:selection>` на строке 470, перед `</dcsset:column>`.

<dcsset:item xsi:type="dcsset:FilterItemComparison">

</dcsset:item>
<!-- стало: удалить; сам блок оформления — внутри группировки колонок: -->
<dcsset:column>
	<dcsset:groupItems>…Период, periodAdditionType Day…</dcsset:groupItems>

вариант «Явки по месяцам» или предупреждение при периоде больше квартала. Это не проверено.

## Чего эта проверка не доказывает

- **Клиент-серверную базу (SQL).** Всё мерилось на файловой базе, одним сеансом. N+1 из «Рисков» на сервере СУБД стоит
  дороже. Блокировки при параллельных сеансах (A11) здесь не проверялись.
- **Отрисовку.** Время клиента (веб или тонкого) на вывод табличного документа в 46–104 тыс. строк или сетки в
  1 129 колонок сюда не входит. Для больших отчётов оно добавится сверху.
- **Динамические списки.** Их повторяют запросы с первой порцией 50 строк и представлениями ссылок. Точный запрос
  платформы (порядок, `ПЕРВЫЕ`, выборка группировок у панели) может отличаться.
- **Числа отчётов.** Деньги в отчётах этот замер не сверяет. Это задача тестов отчётов (N07, B08).
